## Verdict

4924645 is acceptable as a **pre-release**. It is not cleared for client migration.

The third-review findings are fixed in code, with tests that would catch a regression:
- **F1:** a failed generated processor is quarantined, never retried.
- **F2:** a failed open only removes an empty shared directory.
- **F3:** a test-owned ledger checks name-only stops at reply time, and a matching mutant was added.

Other checks:
- The regenerated `GroupControlProcessor` diff contains only failure handling plus version stamps.
- The three commits after 72b6fd4 are real fixes or legitimate synchronisation. No assertion was weakened.
- Full suite, stress, 400 fresh seeds and 30 s chaos all pass on my run.

I found one new runtime defect, of medium-low severity and limited to custom opaque dispatchers. In that setup, a *handwritten* processor's transient failure quarantines a healthy generated peer and kills the group, which exits the JVM under `bootServer`. This contradicts the documented promise that handwritten retry behaviour is "unchanged".

There are also doc gaps:
- The `System.exit` behaviour is absent from the known limits.
- The class javadoc describing #57 is stale.
- The migration gate does not disclose that the public builder's regeneration path can use a remote generator.

None of these blocks a pre-release if they are documented.

## Findings

### N1. Opaque dispatcher: a handwritten failure quarantines healthy generated peers and terminates the group (Medium-Low; runtime)
- **Where:** `EventQueueToEventProcessorAgent.java:211-237`. When `failed == null` (opaque strategy, `failedPosition() == -1`), the code sets `unsafe = subscribed.stream().anyMatch(requiresIsolation)`. This is true whenever *any* generated processor shares the reader, even if the processor that threw is handwritten. It then quarantines every generated candidate and throws a terminal `ProcessorDispatchException`, which extends `AgentTerminationException`. The chain continues:
  - `ComposingEventProcessorAgent.terminateFailedProcessor` marks the group DEAD.
  - Agrona `AgentRunner` (`AgentRunner.java:316-319`) calls `handleError`.
  - Under `bootServer`, that handler is `GlobalErrorHandler.java:20`, which calls `System.exit(-1)`.
- **Input:** a custom strategy with `failedPosition() = -1`, one handwritten processor that throws once (the default retry would absorb it), and one healthy generated processor on the same feed.
- **Evidence:** `review5/OpaqueDispatchHandwrittenFailureTest`, BUILD SUCCESS, 2/2 passing, which confirms the defect.
  - **Control (handwritten only):** 2 attempts, handled once, group RUNNING, no errors.
  - **With the generated peer:** the handwritten processor gets 1 attempt and handles 0 events. The group goes DEAD. The healthy `generated` processor is quarantined with the reason `ProcessorDispatchException ... processor=unknown`; the real cause appears only as the wrapped cause. The error handler receives a `ProcessorDispatchException`.
- **Contract conflict:** `control-plane-contracts.md` says "Ordinary handwritten `DataFlow` retry/cleanup behaviour is unchanged". It describes opaque termination only as a response to a generated failure. The release notes say only "Opaque dispatchers may require ending the group".
- **Suggested fix (either):**
  - Retry under the legacy policy when no failed target can be identified *and* the thrown frame is not inside an `InternalEventProcessor`. A cheap check is the current `ProcessorContext` processor at the time of the throw, which `AbstractEventToInvocationStrategy` sets and the agent could capture.
  - Or document that a custom opaque strategy on a reader with any generated subscriber turns every subscriber exception into group termination and process exit under `bootServer`, and refuse that combination at subscribe time.
  - Either way, include the original cause in the quarantine reason.

### N2. JVM exit on terminal containment is undocumented (Low-Medium; docs)
- Three paths throw `ProcessorDispatchException` to the agent error handler, and under `bootServer` that is `System.exit(-1)`:
  - opaque dispatch
  - "unowned failed subscriber" (`ComposingEventProcessorAgent.isolateFailedProcessor`, around `:95`)
  - "failed quarantine" (around `:117`)
- The contract says only "terminates the group". The rc1 known limits list overload spin-drop and experimental replay, but not `GlobalErrorHandler`'s `System.exit`. That `System.exit` is also the default fate of a generated `start()` failure at boot.
- **Fix:** add a known-limits bullet covering both. Say how to install a non-exiting error handler.

### N3. Stale public javadoc on failure isolation (Low; docs)
- `ComposingEventProcessorAgent.java:66-84` (#57 list) still says, without qualification:
  - a failed runtime `start()` drops the processor and releases everything (tearDown included)
  - a failed `stop()`/`tearDown()` still removes the processor
  - a failed `@ServiceRegistered` handler leaves the processor running
  - "every Throwable is caught … except VirtualMachineError"
- For generated processors, all four are now false: the processor is quarantined, its name is retained, and shutdown is incomplete. A `ProcessorDispatchException` can also escape the catch.
- `MongooseServerConfig.isolateProcessorStartFailuresAtBoot` (`:114-121`) likewise says "the processor is dropped".
- **Fix:** add the generated-processor exception to both javadocs.

### N4. The regeneration gate does not disclose the public builder's remote generator (Low for pre-release, Medium for migration; docs/security)
- `client-migration-1.0.33.md` requires clients to "Regenerate client processors with compiler 1.0.80".
- The public `fluxtion-builder-1.0.80.jar` contains `remote/client/RemoteHttpCombinedGenerator` and `FluxtionConfigManager`. Their strings include the default host `https://fluxtion-source-gen.p.rapidapi.com` and the keys `fluxtion.apiKey` and `fluxtion.remote.host`.
- The pom's `regen` profile says the private `fluxtion-generator-core` makes generation local, with "no API key and no network". Mongoose docs never say that the graph model may otherwise be sent to a third-party endpoint, or which path a client's build takes.
- I did not trace the builder's provider-selection logic, so whether remote is the *default* fallback is unverified.
- **Fix:** add one line to the migration gate and the runtime-upgrade report naming the local versus remote providers and how to force local.

### N5. Prerelease workflow trusts any matching tag (Low; supply chain)
- `.github/workflows/prerelease.yml` publishes to Central on any `v*-rc*` tag push.
- It checks only that the tag matches the POM version. It does not check that the commit is the qualified SHA, or that it is reachable from `main` or the PR head.
- Actions are pinned by major version only (`@v4`), not by SHA, and the signing secrets are passed to the job.
- The procedure relies on humans. Consider a protected tag rule or environment approval, plus SHA-pinned actions.

## Overclaims
1. **Contracts, "Ordinary handwritten `DataFlow` retry/cleanup behaviour is unchanged":** false on opaque readers shared with generated processors (N1).
2. **Contracts and release notes, opaque dispatchers "terminate the group" / "may require ending the group":** under `bootServer` this is process exit (N2).
3. **`ComposingEventProcessorAgent` javadoc for #57, and `isolateProcessorStartFailuresAtBoot`:** these describe pre-quarantine semantics as current behaviour (N3).
4. **The quarantine record's reason** ("processor=unknown") does not identify the cause for the healthy peers quarantined on opaque readers. The evidence is weaker than "names the affected processors and reasons" suggests.
